# Projeto: Evolução do E2E Healer para um fluxo automatizado de manutenção de testes

## 1. Contexto do projeto

Estou trabalhando na evolução de um agente de IA chamado E2E Healer, desenvolvido para auxiliar na manutenção de testes automatizados com Playwright.

Atualmente, temos duas frentes de automação:

- **Smoke Tests:** suíte crítica, bem mantida e que deve permanecer independente e protegida.
- **End-to-End Tests (E2E):** suíte mais abrangente, que contempla os demais cenários de testes automatizados. Atualmente, apresenta um volume significativo de falhas relacionadas à falta de manutenção, testes desatualizados e problemas de automação.

O principal problema é que, mesmo possuindo um agente capaz de diagnosticar falhas e propor correções, ainda dependemos de intervenção humana para identificar os problemas, acionar o agente, acompanhar as correções e encontrar disponibilidade para realizar a manutenção.

O objetivo é evoluir o agente para um fluxo automatizado, integrado à pipeline de E2E, capaz de identificar falhas, investigar suas causas, propor correções, identificar os responsáveis pelos testes e entregar uma Pull Request para revisão humana.

## 2. Objetivo da evolução

Quero investigar a viabilidade de implementar um fluxo em que a própria pipeline de testes E2E acione automaticamente o processo de manutenção sempre que identificar falhas.

O fluxo esperado é:

1. A pipeline E2E executa os testes normalmente.
2. Ao identificar falhas, disponibiliza os resultados, logs e evidências para o processo de manutenção.
3. Um orquestrador aciona o agente E2E Healer.
4. O agente analisa e classifica as falhas.
5. Agrupa ocorrências relacionadas para evitar investigações e correções duplicadas.
6. Investiga a causa raiz de cada grupo de falhas.
7. Consulta o documento de ownership fornecido para identificar a squad e os responsáveis por cada teste.
8. Propõe e aplica as correções em uma branch isolada.
9. Executa novamente os testes afetados e as validações necessárias.
10. Caso a correção seja considerada válida, cria uma Pull Request em Draft.
11. Envia uma notificação direcionada no Google Chat para a pessoa ou squad responsável.
12. A pessoa recebe o diagnóstico, as evidências e o link da PR para revisar, testar e aprovar a correção.

**Importante: não queremos integrar o Jira nesse fluxo.**

A gestão das ocorrências será feita por meio das notificações e das Pull Requests no repositório.

A aprovação e o merge devem permanecer sob responsabilidade humana.

Analise sua estrutura e determine como ele pode ser consumido pelo agente.

- Identificar a responsabilidade de cada arquivo de teste.

- Tratar situações em que não exista correspondência.

Avalie se o documento pode ser consumido diretamente ou se seria melhor transformá-lo em uma estrutura padronizada, como JSON ou YAML.

O documento deve ser tratado como fonte de referência para ownership, sem permitir que o modelo invente responsáveis ou associações.

## 4. Arquitetura desejada

Investigue a possibilidade de implementar os seguintes componentes:

### 4.1. Failure Orchestrator

Uma camada responsável por receber os resultados da pipeline e controlar o processo de manutenção.

Responsabilidades:

- Capturar os testes que falharam.
- Consolidar resultados.
- Agrupar falhas relacionadas.
- Evitar processamento duplicado.
- Acionar o E2E Healer.
- Controlar o estado de cada ocorrência.
- Registrar os resultados do processo.

### 4.2. AI Diagnosis

Utilizar o agente existente para investigar as falhas.

O sistema deve classificar as ocorrências, considerando pelo menos:

- Problemas de manutenção dos testes.
- Regressões reais do produto.
- Falhas de ambiente.
- Testes intermitentes (flaky tests).
- Problemas de massa de dados.
- Falhas inconclusivas.

Somente falhas com evidências suficientes de problemas de manutenção devem avançar para uma proposta de correção automatizada.

O agente não deve modificar testes para mascarar defeitos reais do produto ou problemas de infraestrutura.

### 4.3. Ownership Resolver

Componente responsável por consultar o documento de ownership e identificar a squad responsável.

Deve existir uma estratégia de fallback para situações em que o responsável não possa ser identificado com segurança.

Nesses casos, a ocorrência deve ser encaminhada para uma triagem geral, sem atribuição inventada.

### 4.4. Automated Healing

Reutilizar o E2E Healer existente para:

- Investigar os problemas.
- Propor alterações.
- Gerar patches.
- Aplicar as correções em uma branch isolada.
- Executar os testes afetados.
- Executar testes relacionados quando necessário.
- Registrar as evidências da validação.

Avalie a melhor estratégia para criação e nomenclatura de branches, isolamento de execuções e prevenção de conflitos entre correções simultâneas.

### 4.5. Pull Request Automation

Quando uma correção passar pelas validações, o sistema deverá:

- Criar uma branch de manutenção.
- Aplicar as alterações.
- Criar uma Pull Request em Draft.
- Apresentar o diagnóstico da falha.
- Explicar a causa raiz identificada.
- Descrever as alterações realizadas.
- Informar os testes executados.
- Apresentar os resultados das validações.
- Identificar a squad responsável.
- Incluir links para os logs e evidências originais.

A PR deverá solicitar revisão humana.

O agente não poderá realizar merge, aprovar a própria alteração ou modificar diretamente a branch principal.

### 4.6. Google Chat Notification

Investigue como integrar o fluxo ao Google Chat já utilizado pela equipe.

A notificação deverá ser direcionada à pessoa, squad ou espaço responsável, de acordo com o documento de ownership.

A mensagem deverá conter:

- Identificação do teste ou funcionalidade.
- Descrição resumida do problema.
- Causa raiz identificada.
- Solução proposta.
- Resultado das validações.
- Link da Pull Request.
- Link das evidências da execução.

Evite notificações genéricas ou mensagens repetitivas.

Se não houver uma correção segura, a notificação deverá informar que existe uma falha aguardando investigação humana, sem apresentar uma solução como se estivesse validada.

## 5. Investigação de infraestrutura e credenciais

Esta é uma das partes mais importantes da análise.

Quero que você investigue exatamente o que a infraestrutura atual permite e o que precisaria ser disponibilizado para implementar a solução.

Identifique todas as integrações e credenciais necessárias.

Considere, mas não assuma previamente, a necessidade de:

- Token de acesso ao repositório.
- Permissões para criar branches.
- Permissões para publicar Pull Requests.
- Acesso aos resultados e artefatos da pipeline.
- Credenciais ou autenticação para executar o agente.
- API Key ou autenticação do modelo de IA.
- Acesso ao Google Chat.
- Webhook ou autenticação para envio de mensagens.
- Permissões de execução de scripts.
- Acesso a variáveis de ambiente.
- Armazenamento temporário de resultados e patches.

Para cada dependência, informe:

1. Qual é a finalidade.
2. Por que é necessária.
3. Onde deverá ser configurada.
4. Qual nível de permissão será necessário.
5. Se já existe algo equivalente no ambiente atual.
6. Se existe alguma alternativa mais simples.

Não solicite, exponha ou reproduza valores de secrets. Trabalhe somente com os nomes das variáveis e requisitos de configuração.

Priorize o princípio do menor privilégio.

## 6. Estratégia de execução e segurança

Avalie como implementar o fluxo sem comprometer a estabilidade das pipelines.

Considere:

- Execução isolada do agente.
- Limites de concorrência.
- Timeout por investigação.
- Limite de tentativas de correção.
- Controle de custos e consumo de IA.
- Deduplicação de ocorrências.
- Prevenção de loops de execução.
- Tratamento de falhas do próprio agente.
- Proteção de credenciais.
- Isolamento entre branches.
- Prevenção de alterações fora do escopo dos testes.
- Auditoria das alterações realizadas.

Um ponto especialmente importante: a criação de uma PR não deve gerar um novo ciclo automático de manutenção que fique se repetindo indefinidamente.

Avalie como identificar execuções originadas pelo próprio agente e evitar esse comportamento.

Também avalie como garantir que o agente não tenha acesso irrestrito a credenciais de publicação ou aprovação.

## 7. Cenário esperado de funcionamento

Utilize o cenário abaixo para validar a arquitetura proposta.

Uma execução da pipeline E2E identifica 15 testes falhando.

O sistema:

1. Captura os 15 resultados.
2. Identifica que alguns possuem causas semelhantes.
3. Agrupa as ocorrências relacionadas.
4. Classifica cada grupo.
5. Identifica quais falhas são efetivamente problemas de manutenção.
6. Consulta o documento de ownership.
7. Identifica as squads responsáveis.
8. Aciona o Healer para as correções elegíveis.
9. Cria branches isoladas.
10. Aplica e valida as correções.
11. Abre Pull Requests em Draft para as correções aprovadas pelo processo automatizado.
12. Notifica os responsáveis no Google Chat.
13. Registra quais ocorrências foram corrigidas, quais estão aguardando revisão e quais precisam de investigação humana.

Ao final, cada responsável deve receber somente as ocorrências pertinentes à sua área, com informações suficientes para entender e revisar a solução.
