Você é um engenheiro de QA Automation responsável por refatorar e padronizar a suíte de Smoke Tests da automação E2E deste projeto.

## OBJETIVO

Refatorar os Smoke Tests de todos os mercados:

* Brasil (BRA)
* México (MEX)
* Consul México (CONSULMEX)
* Argentina (ARG)
* Colômbia (COL)

A nova implementação deve substituir o modelo monolítico/fragilizado atual por uma abordagem **modular, atômica, rápida, determinística e específica para Smoke Tests**.

O objetivo dos Smoke Tests NÃO é cobrir profundamente as regras de negócio.

Eles devem funcionar como um **"heartbeat" da aplicação**, respondendo rapidamente:

> "O site está vivo e os principais caminhos críticos estão funcionando?"

---

# 1. PRINCÍPIO FUNDAMENTAL

NÃO reutilize simplesmente os `specs` de Feature existentes adicionando uma tag `smoke`.

Os testes de Feature e os Smoke Tests têm objetivos diferentes.

### Feature Tests

Devem continuar responsáveis por:

* regras detalhadas de negócio;
* cenários positivos e negativos;
* casos de borda;
* diferentes combinações de dados;
* validações detalhadas;
* maior profundidade funcional.

### Smoke Tests

Devem ser responsáveis por:

* validar disponibilidade;
* validar renderização;
* validar os principais caminhos críticos;
* detectar rapidamente regressões graves;
* possuir poucas etapas;
* possuir o mínimo possível de dependências;
* evitar etapas intermediárias desnecessárias;
* serem rápidos e determinísticos.

Portanto:

**Use os Feature Tests como fonte de conhecimento e cobertura existente, mas crie cenários Smoke próprios e dedicados.**

# 4. NOVA ESTRUTURA

O Smoke deve seguir uma arquitetura modular baseada em três pilares:

```text
Smoke
├── Home Availability
├── Catalog PDP Rendering
└── Checkout Viability
```

A implementação esperada é baseada em um arquivo semelhante a:

```text
smoke/
└── modular.spec.ts
```

ou na estrutura equivalente já utilizada pelo projeto.

O arquivo deve ser responsável por organizar os três pilares, mantendo os testes:

* independentes;
* pequenos;
* atômicos;
* fáceis de diagnosticar;
* rápidos;
* específicos para Smoke.

Não transforme `modular.spec.ts` em um novo arquivo monolítico gigante.

Se necessário, utilize helpers, fixtures ou módulos auxiliares para manter a separação de responsabilidades.

---

# 5. HOME AVAILABILITY

Criar Smoke Tests específicos para validar a disponibilidade da Home.

O teste deve responder essencialmente:

> A Home deste mercado está acessível e renderizando o mínimo necessário?

Evite:

* navegar por múltiplas páginas sem necessidade;
* executar regras de negócio;
* validar conteúdo detalhado;
* realizar ações que não sejam necessárias para provar disponibilidade.

O teste deve falhar rapidamente quando a Home estiver indisponível ou quebrada.

---

# 6. CATALOG / PDP RENDERING

Criar Smoke Tests específicos para validar a PDP.

O objetivo é responder:

> Consigo acessar uma PDP válida e os elementos fundamentais da página estão sendo renderizados?

Utilize um produto/SKU especificamente adequado para Smoke.

Não dependa de:

* busca complexa;
* navegação extensa pelo catálogo;
* dados que possam desaparecer;
* produtos aleatórios;
* etapas intermediárias desnecessárias.

Sempre que a arquitetura permitir, prefira acesso direto/deep link à PDP.

---

# 7. CHECKOUT VIABILITY

Criar Smoke Tests específicos para validar que o checkout está funcional.

O objetivo é responder:

> Um usuário consegue chegar ao checkout através do caminho mínimo necessário e o checkout está operacional?

Utilize os arquivos existentes na pasta `/checkout` como referência para entender:

* Page Objects;
* locators;
* etapas;
* dados;
* validações;
* comportamento esperado.

Entretanto, NÃO copie um Feature Test inteiro.

Crie o caminho mínimo necessário para validar a viabilidade do checkout.

---

# 8. TEST DATA

Smoke Tests devem utilizar dados **determinísticos e controlados**.

Um problema crítico a ser evitado é:

> Smoke falhar simplesmente porque um SKU ficou sem estoque ou deixou de existir.

Portanto:

* identifique os SKUs atualmente utilizados pelos mercados;
* identifique quais possuem disponibilidade garantida;
* utilize dados próprios para Smoke sempre que possível;
* evite produtos escolhidos dinamicamente quando isso introduzir instabilidade;
* evite depender de resultados de busca imprevisíveis;
* evite dados que mudem frequentemente.

Para cada mercado, documente claramente qual SKU/dado é utilizado e por quê.

Caso exista configuração específica por mercado, mantenha essa configuração isolada.

Exemplo conceitual:

```text
BRA → SKU próprio de Smoke
MEX → SKU próprio de Smoke
CONSULMEX → SKU próprio de Smoke
ARG → SKU próprio de Smoke
COL → SKU próprio de Smoke
```

Não assuma que o mesmo SKU funciona em todos os mercados.

---

# 9. DEEP LINKS E ATALHOS

Sempre que possível, reduza etapas intermediárias.

Por exemplo:

### Evitar

```text
Home
→ Menu
→ Categoria
→ Subcategoria
→ Busca
→ Produto
→ PDP
```

### Preferir

```text
PDP Deep Link
→ PDP
```

Da mesma forma, quando possível, utilize mecanismos que permitam chegar ao estado necessário do teste sem repetir etapas já validadas por outro Smoke.

O objetivo é reduzir:

* tempo de execução;
* pontos de falha;
* flakiness;
* dependências entre testes.

Importante:

**Não utilize atalhos que deixem de validar o comportamento que o Smoke deveria provar.**

O atalho deve remover complexidade desnecessária, não mascarar uma funcionalidade quebrada.

---

# 10. WAIT FOR TIMEOUT

Remova usos desnecessários de:

```typescript
waitForTimeout()
```

Especialmente waits utilizados apenas para:

* "dar tempo para a página carregar";
* esperar animações;
* compensar race conditions;
* mascarar problemas de sincronização.

Substitua por sincronização baseada em estado observável, utilizando os mecanismos já existentes no projeto, como:

* locator assertions;
* `expect`;
* espera por elementos;
* espera por URL;
* espera por estado de carregamento;
* condições específicas de negócio;
* mecanismos de espera já existentes nos Page Objects.

Não introduza waits arbitrários novos.

---

# 11. REMOVER IF/ELSE DESNECESSÁRIOS

Analise a implementação atual e remova `if/else` utilizados apenas para contornar instabilidade ou diferenças que deveriam estar encapsuladas na configuração do mercado.

Evite padrões como:

```typescript
if (mercado === ...)
```

espalhados pelo teste.

Quando houver diferenças legítimas entre mercados, prefira:

* configuração;
* fixtures;
* test data;
* Page Objects;
* adapters/helpers específicos.

O Smoke deve continuar legível.

---


```text

MEX-SMK-001

CONSULMEX-SMK-001
```

Os IDs devem ser:

* únicos;
* estáveis;
* fáceis de identificar;
* associados ao mercado;
* apropriados para integração com Zephyr.

Não reutilize IDs existentes de outros tipos de teste.

Antes de criar um ID, procure no projeto para garantir que ele não esteja sendo utilizado.

# 14. ISOLAMENTO ENTRE TESTES

Cada Smoke deve ser independente.

Evite:

```text
Smoke 2 depende do estado criado pelo Smoke 1
```

Prefira:

```text
Smoke 1 → independente
Smoke 2 → independente
Smoke 3 → independente
```

Se um teste falhar, os demais devem continuar capazes de executar.

Não crie dependências artificiais entre os três pilares.

### Pergunte:

1. Esse cenário comprova uma funcionalidade essencial?
2. Ele detectaria uma regressão crítica?
3. Ele pode ser executado rapidamente?
4. Ele possui dados determinísticos?
5. Ele possui poucas dependências?
6. Ele pode ser executado isoladamente?
7. Ele representa corretamente o objetivo de um Smoke Test?

Se a resposta for não, não transforme esse cenário em Smoke.

O objetivo não é maximizar a quantidade de Smoke Tests.

O objetivo é maximizar o **sinal de saúde da aplicação com o menor custo e menor instabilidade possível**.

# 19. ANÁLISE DE FLAKINESS

Durante a execução, observe especialmente:

* timeout;
* elementos intermitentes;
* problemas de sincronização;
* SKU sem estoque;
* redirecionamentos;
* carregamento tardio;
* diferenças de ambiente;
* problemas de sessão;
* dependências entre testes;
* problemas específicos de mercado.

Não resolva flakiness simplesmente aumentando timeout.

Investigue a causa.

# 20. REGRAS IMPORTANTES

NÃO:

* copiar Feature Tests inteiros para Smoke;
* apenas adicionar `@smoke` aos testes existentes;
* aumentar timeouts para esconder problemas;
* utilizar `waitForTimeout` sem necessidade;
* criar dependência entre Smoke Tests;
* utilizar dados aleatórios quando dados determinísticos estiverem disponíveis;
* depender de busca/catalog navigation quando um deep link for suficiente;
* criar `if/else` específicos de mercado espalhados pelo teste;
* alterar funcionalidades de produção;
* modificar Feature Tests apenas para fazer o Smoke funcionar;
* remover cobertura funcional existente sem justificativa.

SIM:

* reutilizar Page Objects existentes;
* reutilizar fixtures quando apropriado;
* reutilizar helpers estáveis;
* utilizar Feature Tests como fonte de conhecimento;
* criar cenários Smoke dedicados;
* manter os testes pequenos;
* utilizar dados determinísticos;
* utilizar deep links;
* utilizar waits baseados em estado;
* separar particularidades por mercado;
* criar IDs únicos;
* manter compatibilidade com Zephyr;
* atualizar a pipeline para a nova arquitetura.

```text

```

### Fase 6 — Stability

Remover:

* `waitForTimeout`;

* dependências;
* navegação intermediária desnecessária.

### Fase 7 — IDs / Zephyr

Garantir IDs únicos no padrão:

```text

```

### Fase 8 — Pipeline

Atualizar a pipeline para utilizar exclusivamente a nova estratégia.

### Fase 9 — Validation

Executar e validar os cinco mercados.

### Fase 10 — Final Review

Antes de finalizar, revisar toda a implementação procurando:

* duplicidade;
* complexidade;
* waits;
* dependências;
* dados frágeis;
* diferenças de mercado mal encapsuladas;
* Smoke Tests que deveriam permanecer como Feature Tests.
