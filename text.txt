# PROJETO: FLAKE TEST DETECTOR
## Agente inteligente de detecção, investigação e correção de falhas em testes E2E

# 1. Visão geral

Desenvolva um agente de IA chamado **Flake Test Detector**, especializado em identificar padrões de falhas, investigar problemas de manutenção em testes automatizados e propor correções por meio de Pull Requests.

O agente deverá aproveitar os dados históricos já produzidos pelas pipelines existentes de Test Change Trend, executadas pelo GitHub Actions.

A proposta não é criar um novo executor de toda a suíte de testes nem substituir as pipelines atuais.

Queremos aproveitar os resultados que já existem para identificar quais testes apresentam problemas recorrentes ou sinais de instabilidade.

A partir dessa identificação, o agente deverá investigar exclusivamente os testes candidatos, utilizando Playwright e Playwright MCP quando necessário.

Quando encontrar evidências suficientes de um problema de manutenção, deverá propor uma correção, validar a alteração, criar uma branch e abrir uma Pull Request direcionada aos responsáveis identificados no documento de ownership.

O processo deverá terminar com uma notificação no Google Chat, contendo o diagnóstico e o link da PR.

**Não utilizar Jira em nenhuma etapa.**

# 2. Objetivo principal

Construir um agente que consiga responder continuamente às seguintes perguntas:

- Quais testes estão falhando com frequência?
- Quais testes apresentam comportamento intermitente?
- Quais testes parecem estar desatualizados?
- Quais falhas apresentam uma causa raiz recorrente?
- Quais testes precisam de manutenção?
- Quais falhas representam possíveis regressões reais do produto?
- Quem é responsável por cada arquivo de teste?
- Quais correções podem ser propostas e validadas automaticamente?

O objetivo final é transformar dados históricos de execução em ações concretas de manutenção.

O agente deve reduzir a necessidade de investigação manual e entregar correções prontas para revisão humana.

# 3. Fontes de dados: GitHub Actions e Test Change Trend

Esta é uma das partes mais importantes da arquitetura.

Já existem pipelines de Test Change Trend que executam periodicamente e produzem dados sobre os testes automatizados.

O Flake Test Detector deverá consumir essas informações, evitando criar uma nova rotina de execução de toda a suíte.

## 3.1. Coleta histórica

O agente deverá acessar o GitHub Actions e investigar as últimas 10 execuções válidas das pipelines de Test Change Trend.

Entenda por execução válida aquela que efetivamente concluiu a execução dos testes e disponibilizou dados suficientes para análise.

Não confunda uma execução da pipeline com uma execução individual de teste.

Para cada execução, procure recuperar, quando disponíveis:

- Identificador da execução.
- Data e horário.
- Branch.
- Commit SHA.
- Marca.
- Identificação da pipeline.
- Testes executados.
- Testes aprovados.
- Testes reprovados.
- Testes ignorados.
- Testes que apresentaram retry.
- Resultados individuais.
- Duração.
- Erros.
- Stack traces.
- Screenshots.
- Traces.
- HTML reports.
- JSON reports.
- Outros artefatos relevantes.

Investigue como os dados são armazenados atualmente.

Priorize o reaproveitamento dos relatórios e artefatos existentes.

Não crie um mecanismo paralelo de armazenamento se os dados atuais forem suficientes.

Se os artefatos históricos estiverem expirados ou indisponíveis, identifique essa limitação e proponha uma alternativa.

## 3.2. Estratégia de identificação dos testes

Crie uma forma confiável de identificar o mesmo teste entre diferentes execuções.

Considere:

- Caminho do arquivo.
- Título do teste.
- Test ID.
- Projeto Playwright.
- Marca.
- Identificadores de suíte.
- Outros identificadores disponíveis nos relatórios.

Não utilize somente o título do teste, pois títulos podem se repetir ou ser modificados.

A identificação deve continuar funcionando mesmo quando houver alterações em metadados não relevantes.

# 4. Failure Pattern Analyzer

Crie um componente especializado em analisar o comportamento histórico dos testes.

Ele deverá consolidar as informações das últimas 10 execuções e identificar padrões.

## 4.1. Indicadores

Para cada teste, calcule, quando os dados permitirem:

- Total de execuções.
- Total de falhas.
- Total de aprovações.
- Taxa de falha.
- Quantidade de execuções consecutivas com falha.
- Quantidade de retries.
- Frequência de intermitência.
- Data da última falha.
- Data da última aprovação.
- Recorrência de mensagens de erro.
- Consistência das causas identificadas.

Utilize dados reais. Não invente valores quando alguma informação estiver indisponível.

## 4.2. Classificação das falhas

O agente deverá diferenciar pelo menos as seguintes categorias:

**A. Suspected Test Maintenance**

Problemas possivelmente relacionados à manutenção dos testes:

- Seletores desatualizados.
- Elementos removidos ou modificados.
- Alterações estruturais na página.
- Locators frágeis.
- Assertions desatualizadas.
- Problemas de sincronização.
- Esperas inadequadas.
- Mudanças na estrutura de componentes.
- Problemas na implementação do próprio teste.

**B. Flaky Test**

Testes que apresentam comportamento intermitente, alternando entre sucesso e falha.

Investigar possíveis causas como:

- Race conditions.
- Problemas de sincronização.
- Dependência de estado.
- Concorrência.
- Instabilidade de dados.
- Problemas de sessão.
- Dependência de outros testes.

**C. Product Regression**

Falhas que apresentam evidências de comportamento incorreto da aplicação.

Não alterar o teste para mascarar regressões reais.

**D. Environment Failure**

Falhas relacionadas a:

- Indisponibilidade do ambiente.
- Problemas de rede.
- Serviços externos.
- Infraestrutura.
- Autenticação.
- Instabilidade de dependências.

**E. Test Data Failure**

Problemas relacionados à massa de dados, inconsistência de informações ou pré-condições não atendidas.

**F. Unknown**

Falhas cuja causa não pode ser determinada com segurança.

Essas ocorrências devem permanecer disponíveis para investigação humana.

## 4.3. Priorização

Crie um mecanismo de priorização considerando:

- Taxa de falha.
- Recorrência.
- Antiguidade do problema.
- Criticidade funcional, quando disponível.
- Número de execuções afetadas.
- Confiança do diagnóstico.
- Potencial de correção.

Não utilize uma única taxa de falha como critério absoluto.

Uma falha recente e isolada não deve necessariamente receber a mesma prioridade de um teste que está quebrado há várias semanas.

# 5. Playwright Investigation

Depois de identificar os testes candidatos, o agente deverá investigar os casos individualmente ou em grupos relacionados.

**Não executar toda a suíte E2E novamente.**

O Playwright MCP deverá ser utilizado somente nos testes identificados como candidatos à investigação.

## 5.1. Processo de investigação

Para cada candidato:

1. Localizar o arquivo de teste.
2. Identificar o cenário correspondente.
3. Recuperar os dados históricos.
4. Inspecionar o código atual.
5. Investigar a falha utilizando Playwright MCP.
6. Executar o teste individualmente.
7. Coletar evidências.
8. Comparar o comportamento atual com o histórico.
9. Identificar a causa raiz provável.
10. Determinar se existe uma correção segura.

Quando necessário, executar novamente o caso para diferenciar falha consistente de intermitência.

Não utilizar retries ilimitados.

A quantidade de tentativas deverá ser configurável.

## 5.2. Regras de investigação

O agente deve preservar a intenção original do teste.

Não deve:

- Remover assertions para fazer o teste passar.
- Reduzir validações funcionais.
- Ignorar erros.
- Introduzir esperas arbitrárias sem justificativa.
- Desabilitar testes como solução automática.
- Modificar comportamento da aplicação.
- Alterar configurações da pipeline para esconder falhas.

Qualquer alteração deve ser tecnicamente justificada.

# 6. Ownership Resolver

Existe um documento de ownership que relaciona arquivos, funcionalidades e áreas de produto às respectivas pessoas ou squads responsáveis.

Esse documento será disponibilizado no repositório.

Ele deverá ser utilizado como fonte oficial para identificar os responsáveis pelas correções.

Investigue sua estrutura e implemente um componente capaz de:

- Localizar o arquivo de ownership.
- Interpretar suas associações.
- Relacionar os arquivos de teste às respectivas squads.
- Identificar os responsáveis.
- Identificar os canais de comunicação, quando disponíveis.
- Determinar os revisores adequados para cada PR.

Não inventar responsáveis.

Se um arquivo não estiver mapeado, encaminhar para uma fila de triagem geral.

Se houver mais de um responsável ou ambiguidade, apresentar a situação sem fazer atribuições incorretas.

Avalie se o formato atual pode ser utilizado diretamente ou se precisa ser convertido para JSON ou YAML.

Evite manter duas fontes de ownership divergentes.

# 7. Intelligent Healing

Quando o diagnóstico identificar um problema de manutenção com evidências suficientes, o agente deverá preparar uma correção.

## 7.1. Geração da correção

O agente deverá:

- Inspecionar o código original.
- Identificar a menor alteração necessária.
- Preservar a arquitetura existente.
- Preservar os padrões do projeto.
- Reutilizar os helpers e componentes disponíveis.
- Respeitar a estrutura Page Object Model, quando utilizada.
- Evitar refatorações desnecessárias.

O objetivo é corrigir o problema identificado, não reescrever o teste.

## 7.2. Validação

Antes de publicar qualquer alteração:

1. Aplicar a correção em uma branch isolada.
2. Executar o teste originalmente afetado.
3. Executar testes relacionados quando necessário.
4. Verificar se não houve regressões.
5. Executar as validações estáticas disponíveis.
6. Registrar os resultados.

Se a correção não puder ser validada, não abrir uma PR como solução concluída.

O agente poderá registrar uma sugestão de correção para revisão humana, mas deverá deixar claro que ela não foi validada.

# 8. GitHub Pull Request Automation

Após a validação bem-sucedida, criar uma Pull Request em Draft.

A branch deverá seguir uma nomenclatura padronizada, por exemplo:

`automation/flake-detector/<test-id>`

A PR deverá conter:

## Identificação
- Marca.
- Arquivo afetado.
- Nome do teste.
- Squad responsável.
- Responsável sugerido.

## Histórico da falha
- Número de execuções analisadas.
- Quantidade de falhas.
- Taxa de falha.
- Histórico resumido.
- Evidências relevantes.

## Diagnóstico
- Categoria da falha.
- Causa raiz identificada.
- Explicação técnica.

## Correção
- Alterações realizadas.
- Justificativa.
- Arquivos modificados.

## Validação
- Teste original.
- Testes relacionados.
- Resultado das execuções.
- Evidências.

## Revisão
- Responsável ou reviewer.
- Links relevantes.

A PR deverá ser criada em Draft, solicitando revisão humana conforme as permissões e os mecanismos disponíveis no GitHub.

O agente não poderá fazer merge, aprovar a própria PR ou modificar diretamente branches protegidas.

Avalie também se é melhor criar uma PR por teste, por causa raiz ou por responsável.

Priorize uma estratégia que evite excesso de PRs e preserve a clareza das alterações.

# 9. Google Chat Integration

Após a criação de uma PR, o agente deverá notificar os responsáveis identificados no documento de ownership.

A mensagem deve ser direcionada à pessoa ou espaço adequado.

Modelo ilustrativo:

**Flake Test Detector | Correção disponível**

Marca: Brastemp

Teste: Checkout - Finalização de pedido

Arquivo: `tests/checkout/checkout.spec.ts`

Histórico: 7 falhas nas últimas 10 execuções.

Diagnóstico: seletor desatualizado após alteração estrutural do componente.

Correção: locator atualizado e validado.

Validação:
- Teste original: aprovado.
- Testes relacionados: aprovados.

Responsável: Squad Checkout.

Pull Request: link da PR.

A mensagem deve ser objetiva e conter informações suficientes para que a pessoa entenda o motivo da notificação.

Para ocorrências sem PR, enviar notificações somente quando houver uma necessidade real de intervenção humana.

Evitar mensagens duplicadas em execuções sucessivas.

# 10. Orquestração e execução do agente

Investigue qual deve ser o melhor mecanismo para iniciar o Flake Test Detector.

Considere:

- Execução manual por comando.
- Execução programada.
- Pipeline exclusiva para o agente.
- Execução independente utilizando a API do GitHub Actions.

A decisão deverá considerar o fato de que as pipelines de Test Change Trend já existem e continuam executando normalmente.

Não criar uma nova execução completa de testes apenas para descobrir falhas que já estão disponíveis no histórico.

O agente deverá conseguir processar diferentes marcas e repositórios, respeitando suas configurações.

Investigue também a possibilidade de processar os resultados de maneira incremental.

### Playwright

### Google Chat

Para cada dependência, identificar se já existe no ambiente e qual configuração adicional seria necessária.

Não solicitar nem expor valores de secrets.

Utilizar sempre o princípio do menor privilégio.

# 12. Persistência e deduplicação

O agente precisa manter controle sobre o que já investigou e corrigiu.

Investigue a necessidade de persistir:

- Test ID.
- Arquivo.
- Marca.
- Histórico analisado.
- Fingerprint da falha.
- Diagnóstico.
- Correção proposta.
- Status da validação.
- Branch.
- Pull Request.
- Responsável.
- Notificação enviada.

Evitar:

- Repetir diagnósticos desnecessariamente.
- Abrir múltiplas PRs para o mesmo problema.
- Notificar repetidamente a mesma pessoa.
- Reinvestigar falhas já resolvidas sem evidência de recorrência.

Se uma falha voltar depois de uma correção, o agente deverá reconhecer o histórico anterior e avaliar se é uma nova ocorrência ou se a correção anterior não resolveu o problema.

Avalie uma solução de persistência proporcional à complexidade do projeto.

# 13. Segurança e confiabilidade

Estabeleça regras claras:

- Nunca fazer merge automaticamente.
- Nunca aprovar a própria PR.
- Nunca alterar código de aplicação.
- Nunca modificar a branch principal.
- Nunca mascarar regressões reais.
- Nunca remover assertions para obter aprovação.
- Nunca publicar uma correção sem validação.
- Não processar novamente uma PR já aberta sem necessidade.
- Não criar ciclos recursivos de execução.
- Não expor credenciais em logs ou relatórios.
- Não executar testes fora do escopo identificado sem justificativa.

O agente deve ser conservador quando não houver evidências suficientes.

É preferível não gerar uma PR do que publicar uma correção incorreta.

# 14. Indicadores de resultado

Implemente uma forma de acompanhar a efetividade do agente.

Considere:

- Testes identificados com falhas recorrentes.
- Testes classificados como flaky.
- Testes classificados como problemas de manutenção.
- Diagnósticos concluídos.
- Correções propostas.
- PRs criadas.
- PRs aprovadas.
- Correções rejeitadas.
- Taxa de sucesso das correções.
- Tempo médio entre identificação e PR.
- Recorrência após correção.
- Distribuição por marca e squad.

Os indicadores deverão diferenciar falhas identificadas, correções propostas e correções efetivamente aprovadas.

# 15. Plano de implementação

Desenvolva a solução de forma incremental.

Sugestão de etapas:

**Fase 1 - GitHub Historical Collector**

Acesso às últimas 10 execuções válidas das pipelines existentes e consolidação dos resultados.

**Fase 2 - Failure Pattern Analyzer**

Identificação dos testes com falhas recorrentes, intermitência e possíveis problemas de manutenção.

**Fase 3 - Playwright Investigation**

Execução somente dos testes candidatos e investigação com Playwright MCP.

**Fase 4 - Ownership Resolver**

Identificação dos responsáveis a partir do documento disponível.

**Fase 5 - Intelligent Healing**

Geração e validação das correções.

**Fase 6 - GitHub PR Automation**

Criação das branches e Pull Requests em Draft.

**Fase 7 - Google Chat Integration**

Notificações direcionadas aos responsáveis.

**Fase 8 - Observabilidade**

Indicadores, histórico de investigações, deduplicação e acompanhamento dos resultados.

Ajuste essa ordem caso a análise técnica identifique dependências diferentes.

# 17. Diretrizes finais

- Desenvolver o Flake Test Detector como um agente novo.
- Não assumir que existe um Healer anterior disponível nesta branch.
- Utilizar o documento de ownership existente.
- Aproveitar os dados históricos já produzidos pelas pipelines.
- Não criar uma nova suíte de execução completa.
- Executar localmente somente os testes candidatos identificados.
- Utilizar Playwright MCP na investigação.
- Não integrar Jira.
- Preservar integralmente a suíte Smoke.
- Não modificar as pipelines de Test Change Trend.
- Reutilizar ferramentas e integrações existentes quando tecnicamente viável.
- Fundamentar conclusões em arquivos, configurações e dados efetivamente encontrados.
- Diferenciar fatos confirmados de hipóteses.
- Não inventar permissões, credenciais ou funcionalidades.

**Resultado final esperado:**

Um agente chamado Flake Test Detector capaz de consumir o histórico de execuções das pipelines existentes, identificar testes que precisam de manutenção, investigar suas falhas com Playwright MCP, consultar o documento de ownership, gerar correções validadas, abrir Pull Requests para revisão humana e notificar os responsáveis pelo Google Chat.

A solução deve funcionar como uma camada inteligente de manutenção sobre a infraestrutura de testes já existente, sem exigir que toda a suíte seja executada novamente para encontrar problemas.
