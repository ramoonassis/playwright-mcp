# Projeto: Evolução do E2E Healer - Arquitetura Local CLI e Execução Automatizada

## 1. Contexto

Estamos desenvolvendo uma evolução de um agente de IA chamado E2E Healer, utilizado para manutenção de testes automatizados com Playwright.

Atualmente, temos duas suítes:

- Smoke Tests: suíte crítica, atualizada e que deve permanecer independente.
- End-to-End Tests: suíte abrangente, com diversos testes que atualmente apresentam problemas de manutenção e falhas acumuladas.

Já existe um agente capaz de executar testes, identificar falhas, agrupar ocorrências, investigar causas e propor correções.

O objetivo agora é evoluir essa arquitetura para permitir que o processo de manutenção seja iniciado de maneira controlada, preferencialmente por uma execução local via terminal.

Também queremos manter a possibilidade de uma execução automatizada pela pipeline, como uma segunda modalidade de utilização.

## 2. Objetivo principal

Investigar e propor uma arquitetura em que o E2E Healer possa ser acionado localmente por um comando no terminal.

O usuário deverá conseguir selecionar uma marca ou um escopo específico de testes e iniciar todo o processo de diagnóstico e manutenção.

O fluxo deverá:

1. Identificar os testes pertencentes à marca selecionada.
2. Executar os testes E2E.
3. Coletar os resultados e evidências.
4. Classificar as falhas.
5. Agrupar ocorrências relacionadas.
6. Identificar a causa raiz.
7. Consultar o documento de ownership para identificar a squad responsável.
8. Acionar o E2E Healer para propor e aplicar correções.
9. Executar novamente os testes afetados.
10. Criar branches isoladas.
11. Criar Pull Requests em Draft quando as correções forem validadas.
12. Notificar os responsáveis pelo Google Chat.

Não queremos integração com Jira.

A gestão do processo será realizada por meio das Pull Requests, notificações e registros locais das execuções.

A aprovação e o merge das alterações devem continuar sob responsabilidade humana.

## 3. Primeira frente: execução local via terminal

Esta é a modalidade prioritária da investigação.

Queremos aproveitar a arquitetura atual do agente e adicionar uma camada de execução local.

Investigue como implementar uma interface CLI para iniciar o fluxo.

Exemplos de comandos desejados:

```bash
npm run healer -- --brand=brastemp

npm run healer -- --brand=consul

npm run healer -- --brand=whirlpool-colombia

npm run healer -- --brand=brastemp --scope=checkout

npm run healer -- --brand=brastemp --dry-run

npm run healer -- --brand=brastemp --no-publish

npm run healer -- --status

npm run healer -- --resume=<execution-id>
```

Esses comandos são referências para a interface desejada. Avalie a melhor implementação considerando a estrutura tecnológica existente.

### 3.1. Seleção de marcas

Investigue como identificar os testes relacionados a cada marca.

Considere a possibilidade de existirem:

- Diretórios específicos.
- Arquivos de configuração.
- Tags nos testes.
- Projetos Playwright separados.
- Variáveis de ambiente.
- Diferentes ambientes e URLs.
- Diferentes configurações de execução.

Não presuma como os testes estão organizados. Inspecione o repositório.

Proponha uma estratégia de identificação confiável dos testes por marca.

### 3.2. Execução controlada

A execução local deve permitir controlar o volume de testes processados.

Investigue:

- Paralelização.
- Quantidade de workers.
- Execução em lotes.
- Consumo de memória.
- Consumo de CPU.
- Inicialização dos browsers.
- Tempo máximo de execução.
- Controle de processos.
- Tratamento de interrupções.
- Persistência dos resultados.

Não queremos sobrecarregar a máquina local.

Avalie uma configuração que permita executar uma marca inteira de forma controlada.

Também considere que diferentes marcas podem possuir diferentes configurações de ambiente.

### 3.3. Coleta de evidências

O agente deve coletar informações suficientes para realizar diagnósticos confiáveis.

Investigue o reaproveitamento dos recursos do Playwright:

- Test results.
- HTML report.
- JSON report.
- Traces.
- Screenshots.
- Vídeos, quando disponíveis.
- Logs.
- Informações de timeout.
- Stack traces.

Avalie quais evidências precisam ser armazenadas e por quanto tempo.

Evite encaminhar todos os arquivos desnecessariamente ao modelo de IA.

### 3.4. Processamento inteligente

Após a execução, o sistema deve analisar os resultados.

Não queremos que o agente consuma recursos de IA desnecessariamente.

Proponha uma estratégia em que:

1. Os testes sejam executados normalmente.
2. Os resultados sejam consolidados.
3. Os testes aprovados sejam descartados da etapa de diagnóstico.
4. As falhas sejam agrupadas por semelhança.
5. As falhas duplicadas sejam identificadas.
6. Apenas ocorrências relevantes sejam encaminhadas ao Healer.

Considere também a possibilidade de reutilizar diagnósticos anteriores quando a falha apresentar a mesma assinatura e as evidências não tiverem mudado.

## 4. Segunda frente: integração com pipeline

Além da execução local, queremos investigar a possibilidade de disponibilizar o mesmo fluxo por meio de uma pipeline exclusiva para manutenção.

Não queremos tornar a pipeline Smoke dependente do agente.

Investigue:

- Como a pipeline atual executa os testes E2E.
- Como poderia iniciar o processo de manutenção.
- Como transferir os resultados para o Healer.
- Como executar o agente no ambiente da pipeline.
- Como armazenar os resultados e evidências.
- Como publicar branches e PRs.
- Como notificar os responsáveis.

Compare duas possibilidades:

A. Pipeline de manutenção independente, acionada manualmente.

B. Pipeline de manutenção acionada automaticamente após a identificação de falhas em outra execução.

Não assuma que precisamos implementar as duas.

Apresente vantagens, limitações, requisitos e complexidade de cada alternativa.

## 5. Arquitetura compartilhada

As modalidades local e pipeline devem, preferencialmente, compartilhar os mesmos componentes internos.

Investigue a possibilidade de utilizar:

### Execution Manager

Responsável por controlar a execução, identificar o escopo e acompanhar o estado do processo.

### Brand Resolver

Responsável por determinar quais testes, ambientes e configurações correspondem à marca selecionada.

### Failure Analyzer

Responsável por consolidar, classificar e agrupar as falhas.

### Ownership Resolver

Responsável por consultar o documento de ownership e identificar os responsáveis.

### E2E Healer

Reutilização do agente atual para diagnóstico, geração de patches e aplicação de correções.

### Validation Engine

Responsável por executar os testes novamente e validar as alterações propostas.

### GitHub Integration

Responsável pela criação de branches e Pull Requests.

### Google Chat Integration

Responsável pelas notificações direcionadas aos responsáveis.

Avalie se essa divisão faz sentido considerando a arquitetura atual. Não crie abstrações desnecessárias se os componentes existentes já atenderem às necessidades.

## 6. Integração com documento de ownership

Será fornecido um documento que relaciona os testes e áreas de produto às respectivas squads e responsáveis.

Analise sua estrutura.

Determine:

- Como o documento pode ser consumido.
- Se deve ser convertido para JSON ou YAML.
- Como identificar a responsabilidade de cada arquivo.
- Como relacionar um teste à funcionalidade correspondente.
- Como determinar o canal ou pessoa que deve receber a notificação.
- Como tratar dados ausentes ou ambiguidades.

A associação deve ser fundamentada no documento, sem inventar responsáveis.

## 7. Criação de Pull Requests

O objetivo final é entregar a correção para revisão humana.

Investigue como o agente pode:

1. Criar uma branch isolada.
2. Aplicar o patch.
3. Executar os testes afetados.
4. Validar os testes relacionados.
5. Registrar evidências.
6. Criar uma Pull Request em Draft.
7. Relacionar a PR ao responsável identificado.

A PR deverá conter:

- Nome da marca.
- Arquivos afetados.
- Testes relacionados.
- Descrição da falha.
- Causa raiz identificada.
- Correção aplicada.
- Resultado das validações.
- Evidências.
- Responsável sugerido.

O agente não poderá:

- Fazer merge.
- Aprovar a própria PR.
- Alterar diretamente a branch principal.
- Modificar código de produto.
- Alterar configurações críticas sem autorização.

Investigue também como evitar conflitos entre múltiplas execuções locais.

## 8. Notificações pelo Google Chat

O sistema deve enviar uma mensagem direcionada à squad ou pessoa responsável.

A mensagem deverá apresentar:

- Marca.
- Funcionalidade.
- Testes afetados.
- Resumo do diagnóstico.
- Causa raiz.
- Solução proposta.
- Resultado da validação.
- Link da PR.

Para falhas sem correção segura, deve existir uma notificação de investigação pendente, sem gerar uma PR artificial.

Avalie as opções de integração com Google Chat e os requisitos de autenticação.

## 10. Persistência e retomada de execução

Uma execução pode ser longa.

Investigue a necessidade de um mecanismo local de persistência para registrar:

- ID da execução.
- Marca.
- Testes executados.
- Falhas identificadas.
- Diagnósticos.
- Patches gerados.
- Validações.
- Branches criadas.
- Pull Requests.
- Notificações enviadas.
- Status atual.

Avalie se JSON, SQLite ou outra solução simples seria suficiente.

Queremos evitar que uma interrupção obrigue o usuário a executar novamente todos os testes e repetir diagnósticos já concluídos.

Também precisamos evitar duplicidade de PRs e notificações.
